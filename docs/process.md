# Как у нас делается контент

```
Предложение (Discord) → Разбор → Диздок → Задачи (доска) → Разработка (PR) → master → Тестовый сервер → Релиз
```

Вся работа видна на доске [Lost Light RoadMap](https://github.com/orgs/Lost-Paradise-Project/projects/7) (GitHub Projects).

## Доска

### Статусы

| Статус | Что значит |
|---|---|
| Ожидание | Свободно для взятия в работу: принятая идея, задача или багрепорт без исполнителя |
| В разработке | Есть исполнитель, идёт работа |
| На ревью | Открыт PR |
| Готово | PR смёржен в `master` |

### Поля

- **Направление** - Баг, Код, Прототипы, Спрайты, Звуки, Карты, Локализация, Гайдбук, Другое;
- **Диздок** - ссылка на `docs/design/...`, «нужен» (крупная фича, диздок ещё не одобрен) или «мелочь»;
- **Type** - тип issue:
  - **Bug** - багрепорт, ставится автоматически формами;
  - **Feature** - фича: принятое предложение игроков (в тексте есть строка `Предложение: <ссылка на ветку>`), идея команды или часть диздока;
  - **Task** - техническая работа: рефакторинг, порт, настройка;
- **Milestone** - версия, в которую войдёт задача (см. [Версии](#версии-milestones)).

### Виды

| Вид | Что показывает |
|---|---|
| Задачи | Основная доска по статусам |
| Бэклог | Всё в «Ожидании», по направлениям, баги сверху - отсюда берут задачи |
| Роадмап | Задачи по версиям (milestones) - что войдёт в следующее обновление |
| Мои задачи | Задачи, где вы исполнитель |

### Что происходит само

- новая issue в `Lost-Light` (в том числе багрепорт) попадает на доску в «Ожидание»;
- багрепорты с форм сразу получают тип **Bug**;
- к задаче привязан PR - статус «На ревью»;
- PR смёржен или issue закрыта - статус «Готово»;
- задачу перевели в «Готово» вручную - issue закрывается;
- sub-issues задачи на доске тоже добавляются на доску.

## Версии (milestones)

Milestone - это версия игры: `4.0`, `4.1` и т. д. Заводится в репозитории: **Issues → Milestones → New milestone**, при желании со сроком (*Due date*). У задачи может быть только один milestone. По milestones строится вид «Роадмап», а у самого milestone видно, сколько задач закрыто и сколько осталось.

Как поставить milestone:

- в issue справа - блок **Milestone**;
- на доске в таблице (Бэклог, Роадмап) - ячейка в колонке Milestone;
- на несколько задач сразу - в списке issues репозитория отметить галочками → **Milestone** сверху.

Milestone - это обещание «сделаем к этой версии», поэтому его ставят на разборе, а не всем подряд:

| Что | Milestone |
|---|---|
| Критичный баг (краш, эксплойт, ломает раунд) | Ближайшая версия |
| Баг или фича, которые решили сделать к конкретному релизу | Эта версия |
| Всё остальное | Без milestone - лежит в Бэклоге, пока кто-то не возьмёт |

После релиза milestone закрывается (**Close**), а всё незакрытое из него переносится в следующую версию или снимается с версии.

## 1. Предложение

Идеи игроки и команда пишут в **форум-канал предложений** в Discord: одна идея - одна ветка. Ветка получает тег «На рассмотрении», под ней голосуют и обсуждают.

На разборе `heads` меняют тег:

| Тег | Что дальше |
|---|---|
| Принято | Тот, кто принял, заводит задачу на доске (см. [Задачи](#4-задачи)) с типом **Feature** и ссылкой на ветку, а ссылку на задачу кидает в ветку |
| Отклонено | В ветке пишется причина, ветка закрывается |
| Уже есть / дубль | Ссылка на существующее |
| Реализовано | Ставится, когда фича в релизе |

В GitHub попадают только принятые идеи - репозиторий не засоряется, а игрокам не нужен аккаунт GitHub. Переносит идею тот из `heads`, кто поставил тег «Принято», - сразу, а не «потом пачкой».

Багрепорты приходят напрямую через формы issue и сами попадают в «Ожидание» с типом Bug.

## 2. Разбор

Всё новое в «Ожидании» разбирают `heads`:

- ставят **Направление** и, если решили, к какой версии делать, - **Milestone**;
- **мелочь** (баг, спрайт, текст, число) - в поле Диздок пишут «мелочь», задачу можно брать сразу;
- **крупное** - в поле Диздок пишут «нужен» и назначают автора диздока. Брать такую задачу в разработку можно только после одобрения диздока;
- дубли и невоспроизводимые баги закрывают с комментарием (**Close as not planned**).

## 3. Диздок

Пишется по [шаблону](design/_TEMPLATE.md) и проходит через PR. Одобрение кого-то из `heads` - решение принято: ссылка на диздок вписывается в поле Диздок вместо «нужен». В диздоке обязательно: владелец, заместитель, происхождение (наше или порт), как выключить и удалить. Подробно - в [design/README.md](design/README.md).

## 4. Задачи

Задачи заводит только команда - прямо на доске: **+ Add item** → текст задачи → **Convert to issue** → репозиторий `Lost-Light`. Отдельного шаблона нет, чтобы задачи не создавали посторонние.

Одобренный диздок режется на задачи: по одной на код, прототипы, спрайты, карту, локализацию. Крупную задачу можно разбить на sub-issues. У каждой задачи - Направление, при необходимости Milestone, а в тексте:

```markdown
Диздок: docs/design/<фича>.md (или «мелочь»)
Предложение: <ссылка на ветку в Discord>

**Что сделать**
Конкретно и проверяемо.

**Готово, когда**
- [ ] Работает в игре
- [ ] Есть русская локализация
- [ ] У спрайтов и звуков указаны лицензия и авторы
- [ ] Обновлены диздок и реестр фич (docs/features.md), если что-то поменялось
```

Ссылки на задачи добавляются в таблицу вверху диздока. Взяли задачу - назначьте себя исполнителем и переведите в «В разработке».

## 5. Разработка

- Наш код и ресурсы - только в папках `_LP`.
- Правки в файлах Starlight и SS14 - минимальные, помечены `// LP edit start` / `// LP edit end`.
- Портированный код остаётся в своём namespace (`_Corvax`, `_Goobstation`…), если проекта-источника ещё нет в списке в `LEGAL.md`, добавь его в том же PR.
- В PR - ссылка на диздок (или «мелочь, без диздока») и блок `:cl:` для чейнджлога. Milestone у PR ставить не нужно - он берётся из задачи.
- Если реализация отличается от диздока - диздок обновляется в том же PR.

## 6. Тест и релиз

PR мёржится в `master` - задача закрывается и уходит в «Готово». Дальше `master` проверяется на тестовом сервере и переносится в `stable` с релизом. В какой релиз вошла задача, видно по её Milestone на роадмапе. После релиза milestone закрывается.

Если на тестовом нашёлся баг - заводится новый багрепорт или задача, старую не переоткрываем.

После релиза фича записывается в [реестр](features.md), ветка предложения в Discord получает тег «Реализовано».

## Уход из команды

Перед уходом передайте свои фичи: поменяйте владельца в [реестре](features.md) и в диздоках, снимите себя с задач на доске. Раз в месяц `heads` сверяют реестр - фичи ушедших без передачи уходят заместителям или получают статус «На поддержке».
